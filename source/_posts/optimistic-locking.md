## 问题场景

在业务系统中，经常会有多人同时编辑同一条记录的场景。比如一个工单系统，多个人可能同时在编辑同一个工单；或者一个配置管理页面，多个管理员可能同时修改同一条配置。

如果没有合适的并发控制机制，就会出现「后保存的用户覆盖先保存用户修改」的问题，导致数据丢失。

## 问题分析

典型的问题流程是这样的：

1. 用户A打开记录，开始编辑
2. 用户B也打开同一条记录，开始编辑
3. 用户A先提交，保存成功
4. 用户B点击提交，覆盖了用户A的修改

这种场景在协作类应用中非常常见，我们需要一种机制来避免数据覆盖。

## 解决方案

业界常见的解决方案有三种：悲观锁、乐观锁和实时协作。

### 悲观锁

悲观锁的思路是「先锁住，再操作」。当用户开始编辑时，就对这条记录加锁，其他用户无法编辑，必须等锁释放。

优点是完全避免冲突，缺点是如果用户忘记解锁或者突然离开，就会造成死锁，其他用户无法编辑。

### 乐观锁

乐观锁的思路是「最后判断，有冲突再处理」。不在加锁阶段限制编辑，而是在提交时才判断是否有冲突。

实现方式是给每条记录增加一个版本号字段，读取时记录版本号，提交时比较版本号。如果版本号一致，说明没有被其他用户修改，可以成功保存；如果版本号不一致，说明已经被其他人修改，返回错误提示用户刷新后重新编辑。

这是业界最推荐的方案，Google Docs、Confluence 等产品都采用类似实现。

### 实时协作

实时协作的方案可以让多个用户同时编辑，并且实时看到彼此的修改。这需要复杂的冲突解决算法和实时通信支持，实现成本较高。

## 乐观锁实现

下面用伪代码描述乐观锁的核心实现思路。

### 数据库层面

给需要并发控制的表增加一个版本号字段，初始值为1。

```
表: change
字段:
- id: 主键
- name: 变更名称
- content: 变更内容
- revision: 版本号，默认1
```

### 后端读取

读取记录时，将版本号一起返回给前端。

```
GET /api/changes/123

返回:
{
  "id": 123,
  "name": "修改配置",
  "content": "xxx",
  "revision": 1
}
```

### 后端更新

更新时验证版本号，如果版本号不匹配，返回409冲突。

```
PUT /api/changes/123
Body: {
  "name": "修改配置",
  "content": "yyy",
  "revision": 1
}

# 如果当前revision = 1，没有被修改，保存成功
# 如果当前revision = 2（已被其他人修改），返回409

成功返回:
{
  "id": 123,
  "name": "修改配置",
  "content": "yyy",
  "revision": 2
}

失败返回:
Status: 409 Conflict
Body: {
  "message": "数据已被其他人修改，请刷新后重试",
  "current_revision": 2
}
```

### 前端处理

前端提交时带上版本号，收到409错误时提示用户刷新页面。

```
// 提交时带版本号
payload = {
  name: "修改配置",
  content: "yyy",
  revision: 1
}
updateRecord(123, payload)

// 处理409错误
if (error.status === 409) {
  showError("该记录已被其他人修改，请刷新页面后重新编辑")
  refreshTable()
}
```

## 总结

乐观锁是一种简单有效的并发控制方案，适用于绝大多数业务场景。相比悲观锁，它不会造成死锁；相比实时协作，实现成本更低。

核心要点：
1. 每条记录增加版本号字段
2. 读取时返回版本号
3. 更新时验证版本号
4. 冲突时返回409，提示用户刷新
